The localization output

A pose describes position and orientation.

The estimate contains

  • The robot's position in the map.
  • Its heading, or the direction it faces.
  • The time of the estimate.
  • Uncertainty in its position and heading.

Other packages use it

  • The planner uses the pose, a map, and a goal to choose a route.
  • The controller uses the pose to follow that route.
  • ROS 2 carries the estimate on /ugv/localization/pose, about 30 times per second.

ROS 2 connects software nodes through messages. Subsystem documentation

The estimator uses wheel velocity. It does not use the configured wheel-pose spawn offset as a global position fix. Sensor interfaces

Camera measurements

The robot carries a square AprilTag with a known pattern and a 0.4 m edge.

From pixels to position

  1. Find the tag and its four corners in the image.
  2. Use the tag size and camera calibration to calculate its position.
  3. Apply the camera mount and tag mount offsets to locate the robot's chassis.

Camera calibration

  • Calibration relates pixels to viewing directions.
  • Mount settings describe the camera's position and angle on the drone.
  • The detector receives images and calibration. It has no simulator-position input.
  • A missing or invalid tag produces no position measurement.

The demo uses rendered images at 5 Hz. Calibration comes from known simulation geometry. Perception documentation

Relative position to map position

The correction adapter combines the camera measurement with the drone's pose.

Position calculation

  • The camera gives an offset from the drone to the robot.
  • The adapter rotates that offset into map directions using the drone's orientation.
  • It adds the offset to the drone's map position.

Robot position = drone position + rotated offset

Example in map coordinates

The example offset is already rotated into map coordinates.

Drone position and orientation uncertainty also enter the correction. Measurement design

Coordinates and time

Use the same map

  • The map uses east, north, and up, in meters.
  • GPS latitude and longitude are converted into local map coordinates.
  • PX4 north/east/down coordinates are converted into east/north/up.
  • A configured offset aligns PX4's local origin with the map.

Use the capture time

  • The image keeps the time when the camera captured it.
  • The adapter finds or interpolates the drone pose at that time.
  • A missing time match waits briefly, then expires.
  • Simulation measurements use the same clock.

The correction allows a 0.25 s gap between drone poses and a 0.5 s measurement age. Frames and timestamps

The EKF combines the measurements

An Extended Kalman Filter (EKF) keeps a running estimate. The project uses the ROS package robot_localization.

Predict movement

  • Wheel speed tells the filter how fast the robot moves.
  • IMU heading tells it which direction the robot faces.
  • The filter predicts the next position between position readings.

Correct position

  • GPS or a drone-derived robot position adjusts the prediction.
  • The reported uncertainty controls the weight of a measurement.
  • Checks reject invalid readings and large inconsistent jumps.
  • The filter publishes the combined pose and uncertainty.

Drone corrections update map x/y. The IMU supplies heading and turn rate. Filter inputs

Uncertainty is part of the output

Covariance describes the size and direction of the estimate's uncertainty.

Measurement errors

  • GPS readings vary around the robot's position.
  • Pixel and mounting errors affect the camera measurement.
  • Drone position and heading errors affect the robot's map position.
  • The system reports these errors through its uncertainty model.

Shared position error

  • Robot GPS and drone position can share the same global offset.
  • They can agree while both are wrong.
  • Relative vision cannot identify that shared map offset.
  • A configured uncertainty term stays in the output. It does not detect or remove unknown bias.

Simulation noise and uncertainty settings are test assumptions. Hardware needs measured settings. Shared-error model

Missing measurements

ConditionImplemented behavior
Robot GPS stopsWheel and IMU readings continue. Camera corrections can still provide map position.
The camera loses the tagThe detector stops sending observations. The EKF continues with remaining inputs.
No global position at startupThe estimate starts with large position uncertainty. Navigation waits for an acceptable pose.
PX4 resets its local referenceThe anchor adapter stops output until its map alignment is reset and the adapter restarts.

Camera loss does not immediately stop the robot. Navigation continues only while pose, map, and route checks pass. Outage behavior

Navigation checks the fused pose

Before motion

  • The pose must use the map frame and contain valid values.
  • The pose must be at most 0.5 s old and received within the last 0.5 s.
  • Position standard deviation must be at most 0.5 m.
  • Heading standard deviation must be at most 0.2 radians, about 11 degrees.

Hold and recovery

  • The planner also needs a valid, fresh map. The controller needs a valid, fresh route.
  • Failed checks cause zero velocity commands every 0.1 s.
  • A steady clock catches missing updates even if simulation time freezes.
  • Valid inputs allow navigation to resume.

Standard deviation is not a maximum error guarantee. Goal-associated routes include footprint clearance. A Gazebo actuator watchdog expires missing commands after 0.35 s. Navigation rules

How the system is tested

Localization accuracy

  • Compare estimates with simulator truth at matching times.
  • Run baseline and assisted filters on the same robot sensor messages.
  • Test GPS on, lost during motion, and off from startup.
  • Inject drift, bad observations, outages, and shared position errors.

Perception and navigation

  • Check camera geometry against known target positions.
  • Move an opaque panel in front of the camera, then remove it.
  • Send stale or uncertain poses to the ROS planner and controller.
  • Measure physical goal distance separately from estimated distance.

Simulator truth is used for sensor simulation and scoring. The estimator and navigation do not receive it as their pose. Test methods and results

Work still needed

Further implementation

  • Implement actuator command expiry in a hardware driver; the Gazebo plugin already provides it in simulation.
  • Add an independent global reference to address shared GPS/drone position bias.
  • Measure physical camera calibration and mounting uncertainty.

Further evaluation

  • Test moving occlusion, motion blur, and damaged tags.
  • Test physical wheel slip and uneven terrain.
  • Test representative obstacles with the mapping subsystem.
  • The existing mapper uses image brightness to classify cells.

Hardware operation, uneven terrain, semantic obstacle detection, and unknown shared global bias remain outside the recorded validation.
