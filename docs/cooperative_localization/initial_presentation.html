The planner needs the robot's pose

The planner needs the robot's pose, the terrain map, and the goal in the same coordinate frame. A route can be correct while the robot follows it wrongly if its estimated pose has drifted.

What happens when the robot loses GPS

The subsystem never stops publishing a pose. What changes is how sure it is.

  • GPS gives a global position while it is available.
  • If it drops out, wheel odometry and the motion sensor (IMU) still track movement. Their small errors add up, so the estimate drifts.
  • As the estimate drifts, the uncertainty value (covariance) grows to show the pose is less certain.
  • Drone corrections pull the estimate back toward the true position.

What goes in and what comes out

The estimator combines the measurements that are available and publishes one robot pose for the planner.

Covariance: how uncertain the estimator is about the pose. These interfaces are not implemented yet. Raw topic names, message quality settings (QoS), rates, and noise values are still open.

How the drone helps

The drone acts as a second source of position when the robot's own GPS is not usable.

AssumptionThe drone keeps reliable localization while the robot's GPS is unavailable.
MeasurementThe drone reports a noisy observation of the robot's position relative to itself.
EffectThe correction reduces drift and uncertainty. It does not make the estimate exact.
HardwareUWB radios, AprilTags, or camera tracking could produce this measurement later. The current interface does not require one.

How localization fits the whole project

Localization and traversability are separate. Both publish data in map so route planning can use them together.

The package for this subsystem is cooperative_localization.

Who uses it and how

  • Planner: uses this pose instead of subscribing to raw GPS, odometry, IMU, or drone measurements.
  • Mapping: publishes traversability data in the same ENU map frame.
  • Coordinates: the robot pose, obstacles, routes, and goals all use the same frame.
  • Covariance: reports how uncertain the estimator is about the pose.
  • Frames: the drone's state is PX4 NED (north, east, down). Convert it to the project's map / ENU frame.

How we will test it

Run the same route under three GPS conditions. Compare estimator error and path-following error.

Three cases

  1. Nominal GPS Regular global position updates.
  2. GPS loss without drone assistance Odometry and IMU continue as the estimate drifts.
  3. GPS loss with drone assistance Relative observations correct the estimate during the outage.

What we measure

  • Position RMSE: overall position error.
  • Mean and max error: typical and worst deviation.
  • Heading error: orientation accuracy.
  • Covariance: reported uncertainty versus actual error.
  • Path-following error: effect on downstream navigation.

Goal: test whether drone relative-position updates reduce drift and path-following error during robot GPS loss.

What this subsystem does and does not do

The subsystem estimates the robot's pose. It does not map terrain, generate routes, or control either vehicle.

In scope

  • UGV pose estimation
  • GPS degradation behavior
  • Odometry and IMU fusion
  • Drone relative-position corrections
  • Pose covariance
  • Planner-facing pose output

Not in scope

  • Terrain classification
  • Path generation
  • Drone path planning
  • Full SLAM (mapping and localizing at once)
  • Loss of localization for both vehicles
  • Commitment to UWB or camera hardware

This supports search-and-rescue routes where the robot's GPS may be degraded and the drone still has reliable localization. It does not solve localization if both vehicles lose their global reference.

Steps to begin

Start with data. The filter is the easy part once real sensor data reaches it.

  1. Agree with the simulation and integration subsystem on who adds the robot's sensors and the bridge into ROS 2. This is an open decision and it blocks everything after it.
  2. Add an IMU and a GPS sensor to the ground robot model. Bridge odometry, IMU, GPS, and the true position into ROS 2. The true position is only for making test data and scoring results.
  3. Write a test-sensor node that adds noise to the true position. It outputs GPS with an on and off switch, and a noisy drone reading of the robot.
  4. Run the existing EKF tool on GPS, odometry, and IMU. Add a small relay that publishes the result on the pose topic. The tool outputs a different message type than our contract, so the relay converts it.
  5. Add the drone reading as another input, after converting drone axes from NED to ENU.
  6. Log error against the true position for the three test cases.
